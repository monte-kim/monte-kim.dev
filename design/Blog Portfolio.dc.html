Muroom

Founder Wound down · Aug 2026

Map-based search for music practice studios in Seoul — founded, built, and wound down in ten months.

The product

Musicians in Seoul book practice rooms by calling studios one at a time. Prices, room sizes, and gear lists live in blog posts and Instagram captions, so comparing two neighbourhoods means twenty phone calls. Muroom put all of it on a map.

Pan the map and results update within the viewport. Thirteen filters narrow by room size, hourly price, gear, and opening hours. Every listing was verified by hand — I cold-called 110 owners to confirm the first 130 studios.

Architecture

One Spring Boot service behind an ALB on ECS, with PostGIS doing the spatial work. I ran Postgres on EC2 instead of RDS and replaced the NAT gateway with a NAT instance — both decisions were about keeping a pre-revenue product under $150 a month.

Making analytics 480× faster with a pre-aggregated data model

12 Jul 2026 8 min read 1,284 views

Our analytics endpoints computed everything at request time. At launch, with a few thousand rows, that was invisible. Eighteen months in, a single trainer dashboard was scanning 40M workout records per page load — and p95 latency crossed four seconds.

The shape of the problem

Aggregating on read means cost grows with history. Aggregating on write means cost stays proportional to new data. The fix is conceptually simple — the hard part is migrating a live system to it.

migration.sqlcopy
CREATE TABLE workout_daily_agg (
  member_id   BIGINT      NOT NULL,
  bucket_date DATE        NOT NULL,
  total_reps  INT         NOT NULL DEFAULT 0,
  PRIMARY KEY (member_id, bucket_date)
);
Expand first, migrate readers one by one, contract last. Never make the database do two jobs in one deploy.
